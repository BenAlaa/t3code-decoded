Pairing is not the authentication mechanism used for every request. It is a trust
bootstrap: a short-lived or process-injected credential is exchanged for a
SQLite-backed session. Ordinary HTTP traffic presents that session as a cookie,
Bearer token, or DPoP-bound token. WebSocket upgrades can present a short-lived
ticket that points back to the same current session row.

## The advertised policy describes posture

The server derives an authentication descriptor from runtime mode and whether its
bind host is remotely reachable.

All four environment-server posture rows advertise browser-cookie, Bearer, and DPoP session methods. The contract
also defines `unsafe-no-auth`, but the policy implementation does not produce it at
the implementation. A descriptor is capability and posture metadata; it is not an
authorization bypass.

## Credential lifetime and replay ledger

The classes differ in storage, duration, and consumption semantics. “Token” alone is
too vague to reason about their security properties.

<div class="table-scroll" tabindex="0" role="region" aria-label="Credential lifetime and replay ledger">
<table class="comparison">
  <caption class="sr-only">Credential storage, default lifetime, and replay behavior</caption>
  <thead><tr><th>Credential</th><th>Storage / binding</th><th>Default lifetime / acceptance window</th><th>Use behavior</th></tr></thead>
  <tbody>
    <tr><td>desktop bootstrap seed</td><td>in-memory map; trusted process handoff</td><td>24 hours</td><td>unbounded reuse while process state survives</td></tr>
    <tr><td>ordinary pairing link</td><td>plaintext credential in SQLite row</td><td>5 minutes</td><td>exactly one successful atomic consume</td></tr>
    <tr><td>development startup link</td><td>plaintext credential in SQLite row</td><td>24 hours</td><td>exactly one successful atomic consume</td></tr>
    <tr><td>normal startup link</td><td>plaintext credential in SQLite row</td><td>5 minutes</td><td>exactly one successful atomic consume</td></tr>
    <tr><td>browser or Bearer session</td><td>server-signed token + SQLite session row</td><td>30 days</td><td>reusable until expiry or revocation</td></tr>
    <tr><td>DPoP access session</td><td>signed token with a <code>jkt</code> claim + SQLite session row; bound to a P-256 key</td><td>1 hour</td><td>requires a valid token-bound proof per request</td></tr>
    <tr><td>DPoP proof</td><td>signed JWT + exclusive replay-marker file</td><td>5-minute acceptance window; 5-second future tolerance; no <code>exp</code> claim</td><td>one use for each thumbprint + <code>jti</code></td></tr>
    <tr><td>WebSocket ticket</td><td>server-signed ticket containing session id; row reloaded</td><td>5 minutes</td><td>the pinned issue/verify path records no one-use state</td></tr>
  </tbody>
</table>
</div>

<EvidenceClaim kind="verified" title="One-time consumption is a database race, not a UI convention" refs={["pairing-grant-consumption", "pairing-sqlite-consumption"]}>
  Persisted grants use a conditional SQLite update so two exchanges cannot both win.
  The process-local desktop seed is a different class: it deliberately retains
  unbounded uses so a trusted desktop renderer can establish a fresh session after a
  reload.
</EvidenceClaim>

<Callout title="Pairing rows contain the credential itself" tone="warning">
  Ordinary pairing tokens are persisted verbatim rather than as a one-way digest.
  Short lifetime and atomic one-use consumption or revocation are implemented; OS
  access control over `state.sqlite` remains security-sensitive. Avoid describing the
  credential as hashed or implying that SQLite setup explicitly hardens its file mode.
</Callout>

## Scopes are capabilities, not roles

The contract defines eight independent scopes. A standard client receives five:
`orchestration:read`, `orchestration:operate`, `terminal:operate`, `review:write`,
and `relay:read`. The administrative set adds `access:read`, `access:write`, and
`relay:write`.

<div class="table-scroll" tabindex="0" role="region" aria-label="Authentication scope profiles and delegation rules">
<table class="comparison">

  <thead><tr><th>Path</th><th>Scope result</th><th>Expansion rule</th></tr></thead>
  <tbody>
    <tr><td>desktop bootstrap seed</td><td>administrative set</td><td>seeded by the trusted desktop process</td></tr>
    <tr><td>ordinary one-time link</td><td>standard set unless the issuer supplied another set</td><td>issuance policy owns the grant</td></tr>
    <tr><td>startup link</td><td>administrative set</td><td>created by server startup</td></tr>
    <tr><td>browser-session exchange</td><td>the complete grant set</td><td>the browser path does not request a narrower subset</td></tr>
    <tr><td>Bearer or DPoP token exchange</td><td>requested subset, or the grant set by default</td><td>cannot add a scope absent from the grant</td></tr>
    <tr><td>session delegates another pairing link</td><td>nonempty, unique requested subset</td><td>issuer needs <code>access:write</code> and must hold every delegated scope</td></tr>

<EvidenceClaim kind="verified" title="Administrative is a scope profile, not a bypass bit" refs={["auth-contracts", "pairing-grant-ttls", "pairing-grant-consumption", "auth-session-exchange", "auth-pairing-ticket-upgrade", "auth-delegated-scopes"]}>
  Every resulting session still reaches endpoint and RPC authorization checks. The
  profiles determine which capabilities a session can satisfy; they do not disable
  authorization.
</EvidenceClaim>

<Callout title="Consumption and issuance are not one transaction" tone="warning">
  The conditional SQLite update makes one-time grant consumption race-safe. Session
  issuance happens afterward as a separate operation. If issuance fails after the
  consume succeeds, no compensation restores that grant; the client needs a fresh
  pairing credential.
</Callout>

  The pinned implementation creates exclusive `dpop-proof-*` marker files. A

The browser cookie is set `HttpOnly`, `SameSite=Lax`, and path `/`; the code does not
set an explicit `Secure` attribute. That is one environment-server session shape,
not the credential used by every remote client. Direct hosted pairing stores a
Bearer environment session, while the managed-relay path later establishes a
distinct DPoP-bound environment session. Chapter 50 follows those remote boundaries.
